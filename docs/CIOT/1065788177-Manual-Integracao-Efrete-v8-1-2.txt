Guia do Integrador
Este guia resume o que mudou, o que permanece e o que é necessário implementar para que os TMS integrados ao
efrete estejam aptos a emitir CIOT conforme a Medida Provisória nº 1.343/2026, com vigência a partir de 24/05/2026.
A estrutura de requisição da API do efrete é mantida.

Para fins de comparação, mantivemos os códigos originais da versão 7.1 dos campos, deixando em branco os códigos
dos novos campos. Uma versão futura adequará o documento e ajustará os códigos da estrutura em sua completude.

Esta documentação está passível de ajustes por adequações da API da ANTT e pode ser ajustada, acompanhe as
versões mais atualizadas divulgadas.

Instruções para registro de problemas
Em caso de problemas na documentação e/ou no software entrar em contato abrindo chamado através suporte web em
ambiente de homologação: https://dev.efrete.com.br/Suporte
Para      auxílio   aos    desenvolvedores    e    usuários dispomos     de    uma    FAQ     disponível   em:
https://sistema.efrete.com.br/Suporte/Faq.

Abreviações
Para fins deste documento entende-se:
PEF – Pagamento Eletrônico de Frete instituído na Resolução ANTT Nº 3.658/2011;
CTRC – Conhecimento de Transporte Rodoviário de Cargas;
RNTRC – Registro Nacional de Transportadores Rodoviários de Cargas;
TAC – Transportador Autônomo de Cargas;
ETC – Empresa de Transporte Rodoviário de Cargas;
CTC – Cooperativa de Transporte Rodoviário de Cargas;
CIOT – Código Identificador da Operação de Transporte – código numérico obtido através do cadastramento no Sistema
efrete, de viagem decorrente de contrato de transporte;
Contrato de Transporte – acordo de transporte entre as partes, estabelecido por viagem, que finda na entrega da carga
e pagamento do serviço;
Setup – Conjunto de comandos de configuração do Sistema efrete;
Login – Processo de identificação do utilizador perante um computador, que permite que este o reconheça; entrada no
Sistema efrete;
LogOut – Desconexão do Sistema efrete;
Hash – Sequência de letras/números geradas por um algoritmo de hashing que busca identificar um arquivo ou
informação unicamente. Hashs podem ser usados para saber se os arquivos baixados através da Internet são idênticos
aos distribuídos pelo desenvolvedor.
Token – Conjunto de caracteres utilizados como chave eletrônica.
WebService – solução utilizada na integração de sistemas e na comunicação entre diferentes aplicações, utilizando a
linguagem universal XML para o tráfego de dados, proporcionando que sistemas desenvolvidos em plataformas distintas
sejam compatíveis;
XML (eXtensible Markup Language) – é uma linguagem de marcação utilizada na criação de documentos com dados
organizados hierarquicamente, tais como textos, banco de dados ou desenhos vetoriais. A linguagem XML é classificada
como extensível porque permite definir os elementos de marcação;
XSD (XML Schema Definition) – em sua essência, é um arquivo XML, porém é estruturado de maneira que permite
validar automaticamente outros objetos XML. Um documento XML, para ser considerado válido, deve respeitar as
restrições impostas por um Schema XSD. O XSD contém as regras de preenchimento de conteúdo e de obrigatoriedade
de cada elemento ou grupo de informação do XML;
WSDL (WebServices Description Language) – é uma linguagem baseada em XML utilizada para descrever
WebServices. Trata-se de um documento escrito em XML que além de descrever o serviço, especifica como acessá-lo
e quais as operações ou métodos disponíveis;
SOAP - Protocolo de acesso a objetos. O SOAP serve para a troca de informações e/ou dados através de objetos criados
em diversas linguagens de programação. Com o SOAP é possível criar aplicações para troca de dados entre empresas.
Este protocolo é baseado em XML, o que significa que as aplicações criadas podem ser aceitas em qualquer plataforma
e por qualquer linguagem.

ℹ ContratantesCargaFracionada: array de strings com CPF/CNPJ dos contratantes adicionais. Obrigatório apenas para

A.3 Cenários de emissão
Personas do CIOT
A regra central é: o CIOT reflete sempre a perna executora do transporte.
 Papel                           Definição
 Contatado                       O executor do frete: proprietário do veículo que realiza o transporte, quem receberá o pagamento
                                 final pelo frete. RNTRC validado contra o CPF/CNPJ.
 Contratante                     Quem contratou por último o executor do frete: pode ser o embarcador ou um transportador
                                 intermediário. Quem pagará o executor do frete.
 Regra de emissão                Se o executor emite o CIOT: ele informa seu contratante e o quanto receberá dele.
                                 Se o contratante emite o CIOT: ele informa o executor (contratado) e o valor que será pago.

Composição de veículos de diferentes proprietários
Informar a placa do cavalo trator (automotor), validado contra o RNTRC do Contratado.
Se informar RNTRC do Veículo para a carreta: o sistema valida o vínculo placa-RNTRC e pode rejeitar se não pertencer.
Se houver cavalo-trator, ao menos 1 implemento deverá ser enviado, neste caso informar true no campo
ComposicaoVeicular.

Múltiplos destinos
É possível emitir múltiplos pares de origem e destino para o CIOT TipoViagem Lotação (Padrão) e Fracionado.

Deve ser utilizado o mesmo tipo de dado para origem e destino, se optado por enviar o CEP na origem, deve-se utilizar
o CEP também no destino. Pares com tipo de dados divergentes serão recusados conforme validação da ANTT.

Recomenda-se utilizar latitude/longitude para maior precisão no cálculo de quilometragem e validação do piso mínimo.
Se enviado mais de um par de origem e destino, com tipos de dados diferentes, provavelmente será considerado pela
ANTT o mais específico.

Campos que impactam cálculo de piso mínimo
A ANTT determinou o preenchimento de campos obrigatórios, dependendo do TipoViagem, que são utilizados para
cálculo de piso mínimo. A efrete não realiza qualquer tratamento nos campos AltoDesempenho, RetornoVazio,
ComposicaoVeicular, Eixos. A informação recebida, seja no cadastramento ou no AdicionarOperacaoTransporte, é
exatamente a informação repassada para ANTT.

2. Logon
2.1. Login

Recebe e-mail e senha do usuário, ou o padrão digital do usuário como senha (neste caso sem identificar o usuário) e
retorna um token, que deverá ser guardado para todas as outras requisições. Se o usuário não for encontrado ou estiver
bloqueado, o retorno será NULO.
Nos casos de utilização de um Certificado Digital este método e as utilizações da tag Token dos demais métodos devem
ser desconsideradas, pois a identificação será através do certificado que deve ser enviado em todas as requisições.
Sugere-se, por boas práticas, utilização do certificado digital na requisição.
Não houve alterações desta requisição da versão 7.1 para versão 8.

Nota: O ambiente de homologação por padrão solicita o envio de um certificado digital, mas seu envio não é obrigatório.

Para homologação:
SOAP: https://dev.efrete.com.br/Services/LogonService.asmx]
REST: https://dev.efrete.com.br/Services/Logon/Login

Para produção:
SOAP: https://sistema.efrete.com.br/Services/LogonService.asmx
REST: https://sistema.efrete.com.br/Services/Logon/Login

2.5. Adicionar Operação de Transporte
Definir requisitos necessários para enviar e receber requisições quanto ao frete (Operação de Transporte).

Estrutura versão 7 praticamente mantida, alguns campos foram desobrigados e houve a inclusão dos novos campos da
ANTT. Campos removidos: EmissaoGratuita, BloquearNaoEquiparado, FreteRetorno (substituído), CepRetorno,
DistanciaRetorno, DestinacaoComercial.

Atenção! Os campos de informações bancárias possuem campos condicionais. Deverá ser informado obrigatoriamente
um grupo de campos por tipo de operação:
   -   Dados bancários: InstituicaoBancaria (Código de compensação ou ISPB), Agencia, Conta e TipoConta;
   -   Pix: TipoChavePix, ValorChavePix, possibilidade da ANTT exigir o capo IdentificadorPix e neste caso informar
       um campo de identificação livre.

Se houver o envio de ambas as informações a requisição pode ser negada, opte pelo envio de apenas um grupo.

Se eFRETE: não é obrigatório preencher nenhum campo; uma vez que a programação de depósito, se houver, será feita
posteriormente e há histórico salvo de dados bancários nos cadastros.
Se DepositoAgendado: obrigatório informar um dos grupos para que o pix seja efetivado via chave ou via dados
bancários.
Se TransferenciaBancaria: obrigatório informar um dos grupos para que seja informado para ANTT que o pagamento é
em depósito em conta informado, seja via pix, seja via conta corrente/poupança/pagamento.

Importante! Para o CIOT TipoViagem Padrao (Lotação) com multiplicidade de origens/destinos e que houver vinculação
de pagamento com tipo “QUITACAO”. A quitação será considerada para o primeiro par de viagem informado, garantindo
que todas as demais funcionalidades envolvidas nesta categoria estejam funcionais.

Para uma explicação mais detalhada sobre Quebra e Diferença de Frete consultar o item:
4.4. Unidades de Medidas e Valores (Quebra e Diferença de Frete)

3.    FaturamentoTransportadoraService
3.1.1. Objetivo
Disponibiliza as faturas geradas no período consultado.

Tipos de fatura:
Adiantamento: Esta fatura exibe as transações do tipo Adiantamento e Livre que estão sendo cobradas como Pós-
Pago. Caso existam transações de Adiantamento e Livre nesta fatura com seu valor zerado significa que esses CIOTs
já tiveram seus valores descontados do cliente de forma Pré-Paga.

Quitacao: Esta fatura exibe as transações de Quitação e Estadia que estão sendo cobradas como Pós-Pago

Exemplo de cenário:
01/07/2015 – Faturada gerada pelo Sistema efrete (Fatura01234).
03/07/2015 – Vencimento da fatura gerada dia 01/07, inclusão de multa.
04/07/2015 – Adição de desconto na Fatura01234.

4. Apêndices
4.1. Legenda do Leiaute das Mensagens de Entrada e Retorno dos Serviços
Para facilitar a visualização dos subníveis dentro do XML foi utilizado o sombreamento em cinza dos campos, quanto
mais escuro o tom, mais profundo será o subnível.
Para um melhor entendimento do leiaute das mensagens dos serviços do Pagamento Eletrônico de Frete, estão descritas
a seguir algumas informações importantes.

4.2. Abreviações Utilizadas no Cabeçalho dos Leiautes
A) coluna #: Código identificador do campo. Este código é único por serviço, e identifica o campo correto quando o
mesmo é referenciado por alguma outra coluna do leiaute.
B) coluna Campo: Identificador do nome do campo. Este nome é o mesmo nome que deve ser passado como uma tag
do XML.
C) coluna Pai: Identifica o campo raiz ao qual o campo de valor pertence. Essa identificação se dá pelo Código
identificador do campo.
D) coluna Tipo: Identifica o tipo do dado do valor que deve ser passado no XML. Os valores possíveis para esta coluna
são:




                      efrete — nstech IP Instituição de Pagamento S.A. | Confidencial | Pág. 49 / 53
                                                                                        Manual de Integração efrete | v8.1
               Abreviação           Descrição                    Limite ou Exemplo
               N                    Numérico inteiro             Até 15 Dígitos
               S                    String                       Até 255 caracteres
               DT                   DateTime                     Exemplo: 2011-12-31 00:00:00
               B                    Boolean                      true or false
               DEC                  Decimal                      Exemplo: 0.12345 (admite 5 casas)
               M                    Valor monetário              Dados correspondentes a um valor monetário. Ex:
                                                                 N.00

               A                    Array de bytes               -




E) coluna Ocorrências (Ocor): Identifica, através de dois dígitos separados por um hífen, a obrigatoriedade do campo
e o número de vezes que o mesmo pode aparecer no XML. O primeiro número representa o número mínimo de
ocorrências do campo no leiaute, enquanto o segundo número representa o número máximo de ocorrências do campo
no leiaute. Com isso, quando temos o exemplo 1-1, significa que a tag no XML correspondente ao campo do leiaute é
obrigatória e deve aparecer apenas uma vez. Caso o primeiro dígito seja “0” (zero), indica que o campo é opcional.
Caso o segundo dígito seja N, significa que ele não possui um número máximo de ocorrências, podendo ser passado no
XML uma lista de tags que representam o campo.
F) coluna Tamanho (Tam): Identifica, através de um dígito ou dois dígitos separados por um hífen, o tamanho máximo
e mínimo do valor da tag no XML correspondente ao campo do leiaute. Quando o valor da coluna é de apenas um dígito,
significa que o tamanho deste campo é fixo. Quando o segundo dígito é representado por um N, significa que não há um
tamanho máximo para o valor passado na tag XML. Esta coluna está presente apenas nos campos do tipo S e N.
G) coluna Descrição/Observação: Fornece uma breve descrição do campo do leiaute ou alguma observação
importante que deve ser informada.

4.3. Tratamento de Caracteres Especiais no Texto de XML
Todos os textos de um documento XML passam por uma análise do “parser” específico da linguagem. Alguns caracteres
afetam o funcionamento deste “parser”, não podendo aparecer no texto de uma forma não controlada.
Os caracteres que afetam o “parser” são:
> (sinal de maior),
< (sinal de menor),
& (e-comercial),
“ (aspas),
‘ (sinal de apóstrofe).

Alguns destes caracteres podem aparecer em alguns campos. Para resolver o problema, é recomendável o uso de uma
seqüência de “escape” em substituição ao respectivo caractere.

Ex. Um transportador de razão social EMPRESA DE TRANPORTE & CARGAS LTDA deve ser informado como:
EMPRESA DE TRANPORTE &amp; CARGAS LTDA no XML para não afetar o funcionamento do “parser”.


              Caractere              Sequência de “escape”
          >                          &lt;
          <                          &gt;
          &                          &amp;
          “                          &quot;
          ‘                          &#39;
